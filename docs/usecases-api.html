Use Cases and MVP API

Nine use cases that close the four leaks from PROBLEM.md, the split between the database and the filesystem, a small CRUD API, and the five business-logic endpoints that make the card file exist. There's one single center: the agent composes from the cards, it doesn't repeat an answer.

Future direction. This page sketches the full MVP (use cases, API, hosted). The weekend's real scope is smaller: a local install for one specific professor, defined in openspec/changes/demo-local-backend/ and DECISIONS.md §15. If this page contradicts the code or the spec, they win.
0

Framework and assumptions

  • Transport. DECISIONS.md §4 says "the relay is the API" (Buzz). This document describes the API as resources + operations: today it's implemented as HTTP + JSON (Plan B: our own service + Postgres/SQLite + Agent SDK); if Buzz gets up and running, each operation maps to a Nostr event or a buzz-cli command. What doesn't change either way is section 5.
  • The database is an index; the card file lives in files. Messages, channels, and members go to the DB. Cards are markdown files in data/<course>/; the DB stores only one index row per card (id, path, type, state, version) so listing is fast. If the DB gets deleted, the card file stays intact. If the card file gets deleted, there's no product.
  • The agent is a CLI over a folder. Claude Code (or Codex) runs with cwd = data/<course>/agents/<agent>/, its CLAUDE.md is the ruleset from DECISIONS.md §6, and it returns a JSON with a fixed contract. The server never writes cards on its own: it applies whatever the agent returned.
  • Compile once, compose every time. ingest is the expensive part (reading raw material, understanding it, writing connected cards). answer is cheap and always fresh: it reads index.md, opens ≤5 cards, and composes for whoever is asking. There's no answer cache.
  • Out of scope (not designed here): fine-grained permissions, grading submissions, collaborative editing, search, multi-course support, notifications, work channels beyond their status.

What Buzz gives us, what's ours

Verified against the Buzz README (2026-07-21; see research/2026-08-22-impacto-del-problema-en-2026.md §C8): Buzz memorizes into an event log (Postgres/S3); it has no filesystem wiki, no cards, no supersedes. Each use case's Buzz / ours chips come from here.

Already in Buzz (1-1, to consume)

  • Identity and Nostr keys for people and agents; agents as members with their own channels and an audit trail.
  • Communities, invitations, roles; channels, threads, DMs, reactions.
  • Media upload (the "base document" arrives this way), presence, search, audit log.
  • buzz-cli (the agent posts messages and canvases) and buzz-acp: @mention → invokes Claude Code/Codex → reply. UC4's transport already exists.
  • Canvases (a publishable mirror of a card), Railway deploy, multi-tenant.
Asterisk 1: this holds if just dev comes up (14:00 checkpoint). Under Plan B, this whole column is also ours to build — but it's the mechanical CRUD from §4, not the product. That's why the pipeline is written as a pure applyDelta(agentDir, delta): identical under both plans.

Doesn't exist in Buzz — the product

  • The per-agent filesystem wiki: linked concept cards, index.md, log.md, frontmatter with sources and supersedes, one commit per run.
  • The ada-wiki skill: the two prompts (ingest, answer) and the JSON contract (composedFrom, pagesRead[], delta none|create|enrich|supersede, difficulty).
  • Applying deltas: enriching without duplicating, superseding without editing, states new|updated|superseded|compiling, a card index.
  • Folders with meaning: questions/, difficulties/, about/, people/, and permissions by composition (who mounts what).
  • The "course" layer: channel presets, professor/student roles, a work channel with status.
  • The fork's UI: the card strip, citation pills, the "from the file" stamp, the agent card, state animations. The transport is Buzz's; these components aren't.
Asterisk 2 (open question, DECISIONS.md §12): whether Buzz's canvas supports full markdown with frontmatter, or the card lives in the file and the canvas is a mirror. Resolve before step 3 of the order (§7).

UC4

Question in a thread → answer with citations → understanding stays

P0 · criteria 7.1 · 7.6transport: buzz-acpcontract and delta: ours
ActorSofia asks in #questions "why does my gradient explode?" and mentions @Ada (or Ada is already in the channel and replies in the thread).
Flow
  1. message.created with a mention triggers answer.
  2. The agent reads index.md, opens ≤5 cards, and composes the reply citing by path. If no card covers it, it can go to raw/ (and says so).
  3. It returns a delta of knowledge: none · create (a concept or connection that was missing) · enrich (a new angle on an existing card) · supersede.
  4. The server publishes the message with citation pills, applies the delta, commits, and, if there was a create, closes the thread with a "published as answer" card.
UIThread with citation pills that open the card; a card at the foot of the thread; the new card highlighted in the strip.
EndpointsPOST /channels/:id/messages (triggers it) · POST /agents/:id/answer (internal) · events agent.presence, message.created, page.*
Card file
modules/03-backprop/exploding-gradient.md (read) modules/03-backprop/learning-rate.md (read) questions/why-it-explodes.md ← create: angle + links to both cards difficulties/03-backprop.md ← +1 line (see UC8)
RuleWhat gets archived is the understanding, not the conversation: questions/ is the index of how a topic was asked about, and it points to concept cards. The reply's text itself is never saved as "the answer."
UC5

"The same thing," asked differently → composed from the file

P0 · criterion 7.2 · the moment of the demo100% ours
ActorTwo days later, Ignacio asks "is it normal for the loss to go to NaN in the third epoch with ReLU?" Different wording, different gap: he doesn't know that's the exploding gradient.
Flow
  1. Same pipeline as UC4. The agent finds the exploding-gradient, initialization, and learning-rate cards in index.md.
  2. It composes a new reply for Ignacio: it connects NaN → explosion → initialization, a connection Sofia never needed to make. It didn't re-read the note. It declares composedFrom: "file".
  3. Delta enrich: the exploding-gradient card gains a "How it shows up in practice: NaN with ReLU" section and a link to initialization. Version +1, state updated.
  4. The message carries the mark "from the file · 3 cards · the oldest is 2 days old."
UI"From the file" stamp on the message (the copy today says "already on file," see §8); the card in the strip moves to updated; X-ray mode shows the sources.
EndpointsThe same as UC4. What sets this case apart is the agent's output contract: composedFrom, pagesRead[], delta.kind = "enrich".
Card file
modules/03-backprop/exploding-gradient.md version: 2 → 3 + ## How it shows up in practice: NaN with ReLU + see also [[initialization]] questions/nan-with-relu.md ← index of the angle, points to the card
What it provesThat the second question found understanding already compiled, ready to compose from, and that the card file ended up better than before. Not that "it was already answered."
UC6

One decision supersedes another

P1 · criterion 7.7ours
ActorMartin writes in #general: "Moving the midterm to 09/15, half the class hasn't gotten to backprop yet" and mentions Ada (or Ada ingests #general every N messages).
Flow
  1. The agent detects a decision from the professor that contradicts the decisions/2026-08-10-midterm-date.md card.
  2. Delta supersede: a new card with supersedes: and the rationale citing the message; the old one is not edited.
  3. The server marks the old one superseded, publishes the new one as a decision-type card, commit.
UIDecision card in the channel; the card open in the panel shows "replaces: original-midterm-date"; the old one shows state superseded.
Endpointsanswer pipeline with delta.kind = "supersede". Also available by hand: POST /pages/:id/supersede (used by a person correcting a card).
Card file
decisions/2026-08-22-midterm-to-sep-15.md supersedes: decisions/2026-08-10-midterm-date.md sources: [msg:m-77] decisions/2026-08-10-midterm-date.md (intact; the index marks it superseded)
RuleEnriching ≠ contradicting. Adding an angle is enrich; changing a fact is supersede. The agent decides which; the server doesn't guess.

5

API: business logic

Five operations. The first two are the product; the other three are variants of "apply a delta to the card file" that are worth exposing by hand too.

POST/channels/:id/ingestP0UC3 · "compile once"

Reads the channel's raw sources and turns them into connected cards. Asynchronous: returns a runId and reports progress via events. Run by the channel's community agent (or whichever is specified).

Request
{ "agentId": "ada",
  "sources": ["raw/martin/modules/03-backprop/backprop.md"],   // optional: defaults to everything new in the channel
  "mode": "full" | "incremental" }                             // incremental = only unprocessed raw material
Response · 202
{ "runId": "run_41", "status": "running" }

// then, via SSE:
ingest.progress { runId, step: "reading" | "writing", pagePath? }
page.created    { page }          // one per card, state "compiling" → "new"
run.finished    { runId, pagesCreated: 5, pagesEnriched: 0, commit: "a1f3c2" }
What the server does: mounts the agent's virtual tree (its own folder + raw/ from the channels it's a member of, read-only) → invokes the CLI with the ingest prompt from the ada-wiki skill → waits for the output JSON → scans wiki/ against the index → inserts/updates pages rows → git add -A && git commit -m "ada: ingest 03-backprop (run_41)" → publishes cards. The agent never touches the DB; the server never writes markdown.
POST/agents/:id/answerP0UC4 · UC5 · UC6 · UC8 · "compose every time"

Internal: triggered by message.created on a mention, or a reply in a thread the agent is part of. Also exposed for the demo and for tests. The only place where new knowledge is born outside of ingest.

1 · contextServer gathers the channel, the last 30 messages of the thread or channel, the triggering message, and the asker's role.
2 · presenceEmits agent.presence: thinking.
3 · agentCLI with cwd in its folder. Reads index.md, opens ≤5 cards, composes, cites by path. Only goes to raw/ if no card covers it, and says so.
4 · contractReturns the JSON below. If it has no source, it says it doesn't know and delta.kind = "none".
5 · applyServer writes the delta to files, bumps version/state, commits, indexes, inserts the message with fromFile, emits events, presence back to online.
Request
{ "channelId": "questions",
  "threadId": "t-nan-relu",        // optional
  "messageId": "m-91" }            // the one mentioning the agent
Response · 202
{ "runId": "run_42" }
Agent output (ada-wiki skill contract)
{
  "paragraphs": [[
    { "kind": "text", "text": "Yes, that's the exploding gradient: since ReLU doesn't saturate, so…" },
    { "kind": "cite", "text": "exploding gradient › why",

Decisions this API forces

To resolve before writing the fourth endpoint. None of these have been decided; they're marked open in AGENTS.md.

  1. fromCard becomes plural. Composing implies several cards. Proposal: fromFile: { cardIds: string[]; oldestAgo: string } in types.ts, and the stamp reads "from the file · 3 cards · 2 days ago." Changes demo.ts, message, and card.
  2. A card's id is its path. Avoids a translation table and makes the agent's cite.path directly the UI's pageId. Cost: renaming a file counts as a supersede (consistent with rule 6).
  3. Seven types in the frontmatter, five in the UI. difficulty and person aren't published to channels; they're read from the agent's card. Alternative: add a sixth PageType, "difficulty," visible only in #teachers.
  4. Automatic ingest every N messages (DECISIONS.md says N=20). The MVP keeps it explicit (@Ada ingest or saving channel settings). If turned on, it should be per-channel, and the resulting delta should always be enrich/create, never supersede without a mention.
  5. Cards published by people: where they live (people/<person>/pages/ is a proposal) and whether the community agent ingests them as raw material. Not needed for the demo.
  6. Transport. If Buzz comes up, answer gets triggered via buzz-acp and this API's server is reduced to the card index + applying deltas + events. Worth writing the pipeline as a pure function, applyDelta(agentDir, delta), from the start.
