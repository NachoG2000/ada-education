Casos de uso y API del MVP

Nueve casos de uso que cierran las cuatro fugas de PROBLEM.md, el reparto entre base de datos y filesystem, una API CRUD chica y los cinco endpoints de lógica que hacen que el fichero exista. El centro es uno solo: el agente compone desde las fichas, no repite una respuesta.

Inspiración a futuro. Esta página dibuja el MVP completo (casos de uso, API, hosted). El alcance real del finde es más chico: una instalación local para un profesor puntual, definida en openspec/changes/demo-local-backend/ y DECISIONS.md §15. Si esta página contradice al código o al spec, mandan ellos.
0

Marco y supuestos

  • Transporte. DECISIONS.md §4 dice «el relay es la API» (Buzz). Este documento describe la API como recursos + operaciones: hoy se implementa como HTTP + JSON (Plan B: servicio propio + Postgres/SQLite + Agent SDK); si Buzz levanta, cada operación mapea a un evento Nostr o a un comando de buzz-cli. Lo que no cambia en ningún caso es la sección 5.
  • La base de datos es índice; el fichero vive en archivos. Mensajes, canales y miembros van a la DB. Las fichas son archivos markdown en data/<curso>/; la DB guarda solo una fila de índice por ficha (id, path, tipo, estado, versión) para listar rápido. Si se borra la DB, el fichero sigue entero. Si se borra el fichero, no hay producto.
  • El agente es un CLI sobre una carpeta. Claude Code (o Codex) corre con cwd = data/<curso>/agents/<agente>/, su CLAUDE.md son las reglas de DECISIONS.md §6, y devuelve un JSON con contrato fijo. El servidor nunca escribe fichas por su cuenta: aplica lo que el agente devolvió.
  • Se compila una vez, se compone cada vez. ingest es lo caro (leer raw, entender, escribir fichas conectadas). answer es barato y siempre fresco: lee index.md, abre ≤5 fichas, compone para quien pregunta. No hay caché de respuestas.
  • Fuera de scope (no diseñado acá): permisos finos, corrección de entregas, edición colaborativa, búsqueda, multi-curso, notificaciones, canales de trabajo más allá del estado.

Qué da Buzz, qué es nuestro

Verificado contra el README de Buzz (21/07/2026; ver research/2026-08-22-impacto-del-problema-en-2026.md §C8): Buzz memoriza en un log de eventos (Postgres/S3); no tiene wiki en filesystem, fichas, ni supersedes. Los chips Buzz / nuestro de cada caso salen de acá.

Ya está en Buzz (1-1, consumir)

  • Identidad y llaves Nostr de personas y agentes; agentes como miembros con canales propios y audit trail.
  • Comunidades, invitaciones, roles; canales, threads, DMs, reacciones.
  • Media upload (el «documento base» llega por acá), presencia, búsqueda, audit log.
  • buzz-cli (el agente postea mensajes y canvases) y buzz-acp: @mention → invoca Claude Code/Codex → respuesta. El transporte de UC4 ya existe.
  • Canvases (espejo publicable de una ficha), deploy a Railway, multi-tenant.
Asterisco 1: esto vale si just dev levanta (checkpoint 14:00). En Plan B toda esta columna también es nuestra — pero es el CRUD mecánico de §4, no producto. Por eso el pipeline se escribe como applyDelta(agentDir, delta) puro: idéntico en ambos planes.

No existe en Buzz — el producto

  • La wiki en filesystem por agente: fichas de concepto enlazadas, index.md, log.md, frontmatter con sources y supersedes, un commit por run.
  • El skill ada-wiki: los dos prompts (ingest, answer) y el contrato JSON (composedFrom, pagesRead[], delta none|create|enrich|supersede, difficulty).
  • Aplicar deltas: enriquecer sin duplicar, reemplazar sin editar, estados nueva|actualizada|reemplazada|compilando, índice de fichas.
  • Las carpetas con semántica: preguntas/, dificultades/, about/, people/, y permisos por composición (quién monta qué).
  • La capa «curso»: presets de canales, roles profesor/alumno, canal de trabajo con estado.
  • UI del fork: franja de fichas, pills de cita, sello «desde el fichero», ficha de agente, animaciones de estado. El transporte es de Buzz; estos componentes no.
Asterisco 2 (duda abierta, DECISIONS.md §12): si el canvas de Buzz soporta el markdown completo con frontmatter o la ficha vive en el archivo y el canvas es espejo. Resolver antes del paso 3 del orden (§7).

UC4

Pregunta en un thread → respuesta con citas → la comprensión queda

P0 · criterios 7.1 · 7.6transporte: buzz-acpcontrato y delta: nuestros
ActorSofía pregunta en #dudas «¿por qué me explota el gradiente?» y menciona a @Ada (o Ada está en el canal y responde en el thread).
Flujo
  1. message.created con mención dispara answer.
  2. El agente lee index.md, abre ≤5 fichas, compone la respuesta citando por path. Si no hay ficha que la cubra, puede ir a raw/ (y lo declara).
  3. Devuelve un delta de conocimiento: none · create (un concepto o una conexión que faltaba) · enrich (un ángulo nuevo en una ficha existente) · supersede.
  4. El servidor publica el mensaje con pills de cita, aplica el delta, commitea y, si hubo create, cierra el thread con la tarjeta «publicado como respuesta».
UIThread con pills de cita que abren la ficha; tarjeta al pie del thread; ficha nueva resaltada en la franja.
EndpointsPOST /channels/:id/messages (dispara) · POST /agents/:id/answer (interno) · eventos agent.presence, message.created, page.*
Fichero
modulos/03-backprop/gradiente-que-explota.md (leída) modulos/03-backprop/learning-rate.md (leída) preguntas/por-que-explota.md ← create: ángulo + links a las dos fichas dificultades/03-backprop.md ← +1 línea (ver UC8)
ReglaSe archiva la comprensión, no la conversación: preguntas/ es el índice de cómo se preguntó un tema y apunta a fichas de concepto. Nunca se guarda el texto de la respuesta como «la respuesta».
UC5

«Lo mismo», preguntado distinto → compuesto desde el fichero

P0 · criterio 7.2 · el momento de la demo100% nuestro
ActorDos días después, Ignacio pregunta «¿es normal que con ReLU la loss se vaya a NaN en la tercera época?». Otro lenguaje, otro hueco: no sabe que eso es el gradiente que explota.
Flujo
  1. Mismo pipeline que UC4. El agente encuentra en index.md las fichas gradiente-que-explota, inicialización y learning-rate.
  2. Compone una respuesta nueva para Ignacio: conecta NaN → explosión → inicialización, que Sofía nunca necesitó conectar. No releyó el apunte. Declara composedFrom: "fichero".
  3. Delta enrich: la ficha gradiente-que-explota gana la sección «Cómo se ve en la práctica: NaN con ReLU» y un link a inicialización. Versión +1, estado actualizada.
  4. El mensaje lleva la marca «desde el fichero · 3 fichas · la más vieja hace 2 días».
UISello «desde el fichero» en el mensaje (hoy el copy dice «ya en el fichero», ver §8); la ficha en la franja pasa a actualizada; rayos X muestran las fuentes.
EndpointsLos mismos de UC4. Lo que distingue el caso es el contrato de salida del agente: composedFrom, pagesRead[], delta.kind = "enrich".
Fichero
modulos/03-backprop/gradiente-que-explota.md version: 2 → 3 + ## Cómo se ve en la práctica: NaN con ReLU + ver también [[inicializacion]] preguntas/nan-con-relu.md ← índice del ángulo, apunta a la ficha
Lo que pruebaQue la segunda pregunta encontró comprensión ya compilada sobre la cual componer, y que el fichero quedó mejor que antes. No que «ya estaba respondida».
UC6

Una decisión reemplaza a otra

P1 · criterio 7.7nuestro
ActorMartín escribe en #general: «Muevo el parcial al 15/09, la mitad no llegó a backprop» y menciona a Ada (o Ada ingiere #general cada N mensajes).
Flujo
  1. El agente detecta una decisión del profesor que contradice la ficha decisiones/2026-08-10-fecha-parcial.md.
  2. Delta supersede: ficha nueva con supersedes: y el rationale citando el mensaje; la vieja no se edita.
  3. El servidor marca la vieja como reemplazada, publica la nueva como tarjeta tipo decisión, commit.
UITarjeta de decisión en el canal; ficha abierta en el panel con «reemplaza a: fecha-parcial-original»; la vieja con estado reemplazada.
EndpointsPipeline answer con delta.kind = "supersede". También disponible a mano: POST /pages/:id/supersede (lo usa una persona que corrige una ficha).
Fichero
decisiones/2026-08-22-parcial-al-15-09.md supersedes: decisiones/2026-08-10-fecha-parcial.md sources: [msg:m-77] decisiones/2026-08-10-fecha-parcial.md (intacta; index la marca reemplazada)
ReglaEnriquecer ≠ contradecir. Agregar un ángulo es enrich; cambiar un hecho es supersede. El agente decide cuál; el servidor no adivina.

Filesystem (el fichero)

Repo git, un commit por ingest o delta. Es lo que el grupo posee.

data/rn-2c-2026/
  raw/<persona>/modulos/<nn>-<slug>/…   ← subidas; solo humanos escriben
  agents/<agente>/
    CLAUDE.md                           ← reglas §6
    wiki/
      index.md         ← qué ficha cubre qué; el agente lo lee primero
      log.md           ← qué aprendió, con fecha
      modulos/<nn>-<slug>/<concepto>.md
      decisiones/<fecha>-<slug>.md
      preguntas/<slug>.md        ← índice de ángulos → fichas
      dificultades/<modulo>.md   ← agregado, ve el profesor
    about/<alumno>.md
  people/<alumno>/
    wiki/…                        ← escribe su agente personal
    pages/<slug>.md               ← fichas publicadas por la persona (propuesta)

Frontmatter de cada ficha: type, title, version, valid_from, supersedes, sources, updated. El id de la fila de índice es el path.

5

API: lógica de negocio

Cinco operaciones. Las dos primeras son el producto; las otras tres son variantes de «aplicar un delta al fichero» que conviene exponer también a mano.

POST/channels/:id/ingestP0UC3 · «se compila una vez»

Lee las fuentes crudas del canal y las convierte en fichas conectadas. Asíncrono: devuelve un runId y avisa por eventos. Lo corre el agente de comunidad del canal (o el indicado).

Request
{ "agentId": "ada",
  "sources": ["raw/martin/modulos/03-backprop/backprop.md"],   // opcional: por defecto, todo lo nuevo del canal
  "mode": "full" | "incremental" }                             // incremental = solo raw sin procesar
Response · 202
{ "runId": "run_41", "status": "running" }

// luego, por SSE:
ingest.progress { runId, step: "leyendo" | "escribiendo", pagePath? }
page.created    { page }          // una por ficha, estado "compilando" → "nueva"
run.finished    { runId, pagesCreated: 5, pagesEnriched: 0, commit: "a1f3c2" }
Qué hace el servidor: monta el árbol virtual del agente (su carpeta + raw/ de los canales donde es miembro, solo lectura) → invoca el CLI con el prompt de ingest del skill ada-wiki → espera el JSON de salida → escanea wiki/ contra el índice → inserta/actualiza filas de pages → git add -A && git commit -m "ada: ingest 03-backprop (run_41)" → publica tarjetas. El agente nunca toca la DB; el servidor nunca escribe markdown.
POST/agents/:id/answerP0UC4 · UC5 · UC6 · UC8 · «se compone cada vez»

Interno: lo dispara message.created con mención o respuesta en un thread donde el agente participa. Expuesto también para la demo y para tests. Es el único lugar donde nace conocimiento nuevo fuera del ingest.

1 · contextoServidor junta canal, últimos 30 mensajes del thread o del canal, mensaje disparador, rol de quien pregunta.
2 · presenciaEmite agent.presence: pensando.
3 · agenteCLI con cwd en su carpeta. Lee index.md, abre ≤5 fichas, compone, cita por path. Va a raw/ solo si ninguna ficha cubre y lo declara.
4 · contratoDevuelve el JSON de abajo. Si no tiene fuente, responde que no sabe y delta.kind = "none".
5 · aplicarServidor escribe el delta en archivos, bumpea versión/estado, commitea, indexa, inserta el mensaje con fromFichero, emite eventos, presencia en-linea.

{ "channelId": "dudas",

Decisiones que esta API fuerza

Para resolver antes de escribir el cuarto endpoint. Ninguna la tomé; están marcadas como abiertas en AGENTS.md.

  1. fromPage pasa a plural. Componer implica varias fichas. Propuesta: fromFichero: { pageIds: string[]; oldestAgo: string } en types.ts, y el sello dice «desde el fichero · 3 fichas · hace 2 días». Cambia demo.ts, message y ficha.
  2. El id de una ficha es su path. Evita una tabla de traducción y hace que cite.path del agente sea directamente pageId en la UI. Costo: renombrar un archivo es reemplazar (coherente con la regla 6).
  3. Siete tipos en el frontmatter, cinco en la UI. dificultad y persona no se publican en canales; se leen desde la ficha del agente. Alternativa: agregar un sexto PageType «dificultad» visible solo en #profesores.
  4. Ingest automático cada N mensajes (DECISIONS.md dice N=20). El MVP lo deja explícito (@Ada ingest o guardar settings del canal). Si se activa, conviene que sea por canal y que el delta resultante sea siempre enrich/create, nunca supersede sin mención.
  5. Fichas publicadas por personas: dónde viven (people/<persona>/pages/ es propuesta) y si el agente de comunidad las ingiere como raw. Para la demo, no hace falta.
  6. Transporte. Si Buzz levanta, answer se dispara por buzz-acp y el servidor de esta API queda reducido al índice de fichas + aplicar deltas + eventos. Conviene escribir el pipeline como función pura applyDelta(agentDir, delta) desde el principio.
