Cómo funciona Ada

Inspiración a futuro. Esta página describe la arquitectura completa hacia donde crece Ada, no el código de hoy. Lo que se construye este finde es la fila «laptop» de la sección 6: una instalación local para un profesor puntual (DECISIONS.md §15, spec en openspec/). Si esta página contradice al código o al spec, mandan ellos.

Una página para entenderlo una vez y no tener que volver a armarlo en la cabeza. No es un SaaS clásico, y ahí está la mitad de la confusión: el modelo de IA no corre en nuestro servidor, corre en un «enchufe» que cada persona conecta desde su máquina.

1. Por qué no es «frontend + API + DB + agente»

En un SaaS clásico la API llama al modelo con la API key de la empresa: la empresa paga, controla y es responsable. En Ada el server nunca llama a un modelo. Es un chat con archivo: guarda mensajes, miembros, canales y fichas publicadas, y avisa por WebSocket cuando algo pasa. La inteligencia entra por el runner: un proceso chico que corre donde viven las credenciales de quien creó el agente, y que usa el programa de IA que esa persona ya tiene (claude, codex, pi con un modelo abierto).

La analogía más útil: runners de GitHub Actions. GitHub guarda el repo y la cola de trabajos; el runner puede ser el de GitHub (pago, siempre prendido) o uno tuyo en tu máquina (gratis, se apaga cuando la apagás). Mismo resultado, distinto quién paga y quién lo mantiene vivo.

3. Qué pasa cuando Sofía escribe @ada

  1. Sofía escribe en el thread. El cliente hace un POST; no sabe que Ada es un agente.
  2. El server guarda el mensaje y ve @ada en el texto. Si el runner de Ada no está conectado, acá termina: el mensaje queda, Ada figura desconectada.
  3. Le manda la mención al runner, con los últimos 20 mensajes del thread (la «capa inmediata» de DECISIONS §6).
  4. El runner arma un prompt (quién pregunta, contexto, pregunta) y ejecuta claude -p con cwd en la carpeta de Ada. No le pasa la wiki: eso lo lee el runtime.
  5. Claude lee CLAUDE.md (las reglas), wiki/index.md, abre hasta 5 fichas, y si la pregunta es reutilizable escribe una ficha nueva. Responde citando con [[preguntas/explota.md]].
  6. El runner compara wiki/ antes y después: lo que cambió se publica. Si no cambió nada y hay una cita, la respuesta se marca «desde la ficha». Hace un commit.
  7. Publica la ficha y el mensaje (las citas ya convertidas a pills).
  8. Todos lo ven en vivo: la ficha en la franja del canal, la respuesta en el thread, Ada vuelve a «en línea».

4. «¿Por qué data/ está en el repo al lado de apps/?»

Porque este finde todo corre en una laptop y necesitamos un curso de ejemplo que se clone con el código. Pero son dos cosas distintas, y conviene tenerlo claro desde ahora:

El repo = código + un curso de ejemplo

apps/web          cliente
apps/server       server
packages/runner   ada-runner
packages/protocol tipos y eventos
data/redes-…/     curso de ejemplo (seed)

Se publica en GitHub. Cualquiera lo clona y tiene la demo andando.

En uso real, la carpeta vive donde vive el runner

~/ada/cursos/redes-2c/agents/tutor/   ← laptop de Sofía
/srv/ada/cursos/redes-2c/agents/ada/  ← Railway del profe
/vol/ada/<tenant>/agents/…/           ← nuestro hosting

El runner recibe --cwd y apunta a cualquier lado. El server nunca ve esa carpeta: solo recibe lo que el runner publica.

5. «Claude ve todo el filesystem, ¿no?» El aislamiento, en tres capas

Sí, técnicamente Claude Code puede ver lo que el sistema operativo le deje ver. La pregunta correcta es cuánto aislamiento necesita cada tier, porque no es el mismo problema en la laptop de Sofía que en un servidor nuestro con cien agentes de cien personas.

CapaCómoQué garantizaCuándo
1 · política cwd en la carpeta del agente; --add-dir solo para raw/; --allowedTools acotado; reglas deny por path en .claude/settings.json de la carpeta; sin Bash salvo git add/commit. Claude Code se niega a leer/escribir fuera. Es una regla que el runtime cumple, no un muro. Este finde, y el tier local para siempre: en tu laptop, todo ya es tuyo. Si corrés tu agente en tu máquina, no hay a quién aislar.
2 · muro Un contenedor (o micro-VM) por agente. Se montan solo dos cosas: raw/ del curso en solo lectura y la carpeta del agente en lectura/escritura. Nada más existe adentro. Aislamiento del sistema operativo. Aunque el modelo quiera, no hay otra carpeta que leer. Tier hosted v1 (nosotros) y, opcionalmente, el Railway del profe. Es Docker común; no hace falta hostear nada nuevo.
3 · composición Cada agente ve un árbol virtual armado con las carpetas de los canales donde es miembro + la suya (DECISIONS §6, «permisos = composición de carpetas»). Con bind mounts hoy; con Archil cuando sea multi-máquina. Lo mismo que la capa 2, pero la vista del agente cambia cuando lo agregan o sacan de un canal, sin reconfigurar nada. Cuando haya varios agentes compartiendo conocimiento entre canales. No hace falta ni este finde ni para el tier local.
Sobre Archil. Sí: Archil es un servicio hosteado (discos montables respaldados en S3), así que usarlo implica el tier hosted. Pero Archil no es lo que da aislamiento, es lo que da la vista compuesta de la capa 3. El aislamiento lo da la capa 2 con un contenedor por agente, que podemos hacer hoy sin ningún servicio externo. Orden sensato: capa 1 ahora → capa 2 cuando hosteemos → capa 3 cuando haga falta compartir carpetas entre agentes.

7. Preguntas que ya nos hicimos

¿Un profesor puede usar su suscripción de Claude en Railway?

Sí, si lo que corre es el binario claude sin modificar y él se loguea con el flujo de Anthropic (claude setup-token). La página legal de Claude Code lo dice textual: «Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code». Lo que nosotros no podemos hacer es pedir, guardar o rutear ese token. Fuente y detalle: research/2026-08-22-suscripciones-runners-buzz-pi.md.

¿Y pi.dev? Quería no depender de un solo proveedor.

pi es el harness correcto para eso: 15+ proveedores, modelos abiertos vía Ollama/OpenRouter, modo headless, lee CLAUDE.md. Lo que no da es suscripciones: su login OAuth con Claude es justo lo que Anthropic prohibió (desde abril 2026 responde «Third-party apps now draw from your extra usage»). Entonces: pi = runtime con API keys y modelos abiertos; claude/codex = runtime con suscripción. El runner los trata igual.

¿Por qué el server no llama al modelo «aunque sea para la demo»?

Porque es la decisión que no se puede deshacer después. En cuanto el server tiene una API key, hay que guardarla, rotarla, cobrarla, y el tier local deja de ser gratis y privado. Separar server y runner cuesta una tarde hoy y nada mañana.

¿Qué pasa si el alumno apaga la compu?

Su agente personal queda «desconectado» en la UI. Las menciones no se encolan: se pierden, con un aviso al escribir. Es exactamente lo que hace Buzz. Si quiere que esté siempre, lo pasa al tier hosted.

¿Modelos open source?

Entran por pi (Ollama local, vLLM propio, OpenRouter). En hosted son el default barato. No hay problema de términos con nadie.

¿Por qué no forkeamos Buzz al final?

No levantó antes del checkpoint de las 14:00 y ya teníamos un cliente propio. Copiamos su topología (relay que no corre agentes + harness aparte + runtimes del proveedor), no su código. DECISIONS §7 quedó reemplazada por §14.

¿Cómo se cobra?

Solo en hosted: hosting + runner siempre prendido + tokens (por uso o por asiento; no decidido) + backups y analíticas para la institución. Local y self-host son gratis, Apache-2.0.

8. Glosario

Comunidad
Un curso. Un server = una comunidad este finde.
Canal
Estable (#dudas, #03-backprop) o de trabajo (un TP; solo diseño este finde).
Ficha
Una página markdown con tipo, versión, fuentes y «reemplaza a». Es la copia publicada de un archivo de la wiki de un agente.
Agente
Identidad en la comunidad + carpeta + runner. De comunidad (lo crea el profesor) o personal (lo crea un alumno).
Runner
ada-runner: el proceso que conecta un agente al server y ejecuta su runtime.
Runtime
El programa de IA que piensa: claude, codex, pi. Sin modificar, con las credenciales de su dueño.
Wiki
wiki/ dentro de la carpeta del agente: index.md, log.md, modulos/, preguntas/, decisiones/, dificultades/.
Ingest
@agente ingest: leer lo nuevo en raw/ y compilarlo en fichas. No es por mensaje.
Desde la ficha
Respuesta que cita una ficha existente sin escribir nada nuevo. El sello «ya en el fichero · hace N días».
supersedes
Una ficha nueva que reemplaza a otra. La vieja no se edita: pasa a «reemplazada».
Capa inmediata
Los últimos 20 mensajes del canal o thread, que el server manda con cada mención.
