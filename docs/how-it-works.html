How Ada Works

Future direction. This page describes the full architecture Ada is growing toward, not today's code. The current issue #1 foundation is a local multi-community server and web client with opt-in local Claude/Codex subscription runners (DECISIONS.md §22). Deployment and hosted runners remain later work. If this page contradicts the code, GitHub issue #1, or DECISIONS.md, those sources win.

One page to understand it once, so you never have to piece it back together in your head. This isn't a classic SaaS, and that's half the confusion: the AI model doesn't run on our server — it runs on a "plug" that each person connects from their own machine.

1. Why it isn't "frontend + API + DB + agent"

Issue #1 current demo: one global user identity can belong to many communities, with a role per membership. The default shadcn workspace provides the community rail, channels, DMs, members, threads, invites and agent setup. Cards remain backend memory; their dedicated UI is not mounted yet. In a classic SaaS, the API calls the model with the company's API key: the company pays, controls, and is responsible. In Ada the server never calls a model. It's a chat with storage: it stores messages, members, channels, and published cards, and notifies over WebSocket when something happens. Intelligence comes in through the runner: a small process that runs wherever the credentials of whoever created the agent live, using the AI program that person already has (claude or codex).

Browser and runner WebSockets authenticate with a token in their first protocol frame; tokens are not placed in URLs, snapshots, events, logs, or provider prompts. REST paths carry the selected community, while the bearer token identifies the global user.

The most useful analogy: GitHub Actions runners. GitHub keeps the repo and the job queue; the runner can be GitHub's own (paid, always on) or one of yours on your machine (free, turns off when you turn it off). Same result, different question of who pays and who keeps it alive.

An agent is the sum of the last three plus an identity on the server. If the runner isn't connected, the agent exists as a member but shows as "offline": you can mention it, it won't answer. That's not a bug — it's what happens when a student turns off the computer running their personal agent.

3. What happens when Sofia types @ada

  1. Sofia writes in the thread. The client does a POST; it doesn't know Ada is an agent.
  2. The server saves the message and sees @ada in the text. If Ada's runner isn't connected, it stops here: the message stays, Ada shows as offline.
  3. It sends the mention to the runner, along with the thread's last 20 messages (the "immediate layer" from DECISIONS §6).
  4. The runner builds a prompt (who's asking, context, question) and runs claude -p with cwd in Ada's folder. It doesn't pass it the wiki: the runtime reads that on its own.
  5. Claude reads CLAUDE.md (the rules), wiki/index.md, opens up to 5 cards, and if the question is reusable, writes a new card. It replies citing [[questions/explodes.md]].
  6. The runner compares wiki/ before and after: whatever changed gets published. If nothing changed and there's a citation, the reply gets marked "from the file." It makes a commit.
  7. It publishes the card and the message (citations already turned into pills).
  8. Everyone sees it live: the card in the channel's strip, the reply in the thread, Ada goes back to "online."

4. "Why is data/ in the repo next to apps/?"

Because today everything runs on a laptop, and we need a sample course that gets cloned along with the code. But these are two different things, and it's worth being clear about that from the start:

The repo = code + a sample course

apps/web          client
apps/server       server
packages/runner   ada-runner
packages/protocol types and events
data/neural-…/    sample course (seed)

It's published on GitHub. Anyone can clone it and have the demo running.

In real use, the folder lives wherever the runner lives

~/ada/courses/neural-networks-2026/agents/tutor/   ← Sofia's laptop
/srv/ada/courses/neural-networks-2026/agents/ada/  ← the professor's Railway
/vol/ada/<tenant>/agents/…/           ← our hosting

The runner receives --cwd and can point anywhere. The server never sees that folder: it only receives what the runner publishes.

5. "Claude can see the whole filesystem, right?" Isolation, in three layers

Yes, technically Claude Code can see whatever the operating system lets it see. The right question is how much isolation each tier needs, because it isn't the same problem on Sofia's laptop as on one of our servers running a hundred agents for a hundred people.

LayerHowWhat it guaranteesWhen
1 · policy cwd in the agent's folder; bounded read-only excerpts in the prompt; scoped read/write tools; no extra --add-dir root and no provider API keys passed by Ada. Claude Code refuses to read or write outside it. It's a rule the runtime follows, not a wall. Today, and the local tier forever: on your laptop, everything is already yours. If you run your agent on your own machine, there's no one to isolate it from.
2 · wall A container (or micro-VM) per agent. Only two things get mounted: the course's raw/, read-only, and the agent's folder, read/write. Nothing else exists inside. Operating-system-level isolation. Even if the model wanted to, there's no other folder to read. Hosted tier v1 (us) and, optionally, the professor's Railway. It's plain Docker; no need to host anything new.
3 · composition Each agent sees a virtual tree built from the folders of the channels it's a member of, plus its own (DECISIONS §6, "permissions = folder composition"). With bind mounts today; with Archil once it's multi-machine. The same as layer 2, but the agent's view changes when it's added to or removed from a channel, with no reconfiguration. Once several agents share knowledge across channels. Not needed today, nor for the local tier.
About Archil. Yes: Archil is a hosted service (mountable disks backed by S3), so using it implies the hosted tier. But Archil isn't what provides isolation — it provides the composed view in layer 3. Isolation comes from layer 2, with one container per agent, which we can do today with no external service. Sensible order: layer 1 now → layer 2 once we host → layer 3 once agents need to share folders.

7. Questions we've already asked ourselves

Can a professor use their Claude subscription on Railway?

Yes, as long as what's running is the unmodified claude binary and they log in through Anthropic's own flow (claude setup-token). Claude Code's legal page says it outright: «Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code». What we can't do is request, store, or route that token. Source and detail: research/2026-08-22-subscriptions-runners-buzz-pi.md.

What about pi.dev? I wanted to avoid depending on a single provider.

pi is the right harness for that: 15+ providers, open models via Ollama/OpenRouter, headless mode, reads CLAUDE.md. What it doesn't give you is subscriptions: its OAuth login with Claude is exactly what Anthropic banned (since April 2026 it responds "Third-party apps now draw from your extra usage"). So: pi = runtime with API keys and open models; claude/codex = runtime with a subscription. The runner treats them the same.

Why doesn't the server call the model, "even just for the demo"?

Because it's the decision you can't undo later. The moment the server holds an API key, you have to store it, rotate it, bill for it, and the local tier stops being free and private. Keeping server and runner separate costs an afternoon today and nothing tomorrow.

What happens if the student turns off their computer?

Their personal agent shows as "offline" in the UI. Mentions don't get queued: they're lost, with a warning shown when writing. That's exactly what Buzz does. If they want it always on, they move it to the hosted tier.

Open source models?

They come in through pi (local Ollama, your own vLLM, OpenRouter). On hosted, they're the cheap default. No terms-of-service issue with anyone.

Why didn't we fork Buzz in the end?

It wasn't up and running before the 14:00 checkpoint, and we already had our own client. We copied its topology (a relay that doesn't run agents + a separate harness + provider runtimes), not its code. DECISIONS §7 was superseded by §14.

How does billing work?

Only on hosted: hosting + an always-on runner + tokens (usage-based or per-seat; not decided) + backups and analytics for the institution. Local and self-host are free, Apache-2.0.

8. Glossary

Community
A course. One local server can hold several communities today.
Channel
Steady (#questions, #03-backprop) or a work channel (an assignment; design-only today).
Card
A markdown page with a type, version, sources, and "replaces." It's the published copy of a file from an agent's wiki.
Agent
An identity in the community + a folder + a runner. Community (created by the professor) or personal (created by a student).
Runner
ada-runner: the process that connects an agent to the server and runs its runtime.
Runtime
The AI program that does the thinking: claude, codex, pi. Unmodified, with its owner's credentials.
Wiki
wiki/ inside the agent's folder: index.md, log.md, modules/, questions/, decisions/, difficulties/.
Ingest
@agent ingest: read what's new in raw/ and compile it into cards. Not triggered per message.
From the file
A reply that cites an existing card without writing anything new. The "already on file · N days ago" stamp.
supersedes
A new card that replaces another. The old one isn't edited: it becomes "superseded."
Immediate layer
The last 20 messages in the channel or thread, which the server sends with every mention.
