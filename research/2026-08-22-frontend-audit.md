# Frontend audit — apps/web

## Why

An MVP-readiness audit of `apps/web` ahead of, and now re-verified against, the connected-mode work (`openspec/changes/demo-local-backend`, group 5): accessibility, performance, responsiveness, theming (against `DESIGN.md`'s named rules), and implementation integrity (dead controls, honest disabled states). A separate browser pass checked the app actually runs. This file is the record of what the audit found, what got fixed, what's still open, and what a person needs to decide, per `AGENTS.md`'s "all information lands in the repo" rule.

**Why this is a second pass, not a copy of the first.** The audit's fixes landed first; group 5's connected-mode implementation (`lib/api.ts`, `who-are-you.tsx`, `boundary.tsx`, the composer's `@`-mention flow, live presence, `card.published`) landed afterward, in the same session, touching nearly every file the audit had just fixed — `App.tsx`, `lib/community.tsx`, `screens/Channel.tsx`, `components/ada/channel.tsx`, `message.tsx`, `card.tsx`, `panel.tsx`, `components/app-sidebar.tsx` all grew or were rewritten in the hour after the fixes were verified (file mtimes range from 21:47 to 22:35; the fixes were verified at 21:13). Every file:line reference in **What was fixed**, **What remains**, **Open decisions** and **Server notes** below was re-checked directly against the current working tree in this session (`grep -n`, direct reads, `stat`/`git log` for timing) — none are carried over from the first draft of this file, and a few numbers and one implementation detail (noted inline) changed as a result.

## Server notes for Codex

- **No CORS, by design.** `apps/server` sends no CORS headers on purpose (see the comment at `apps/web/vite.config.ts:6-9`): in dev, the SPA reaches it through Vite's proxy (`/api` → `ADA_SERVER`, `/ws` → the same host with `ws: true`, `vite.config.ts:21-24`), so `VITE_ADA_SERVER=/` is same-origin and nothing needs configuring on the server side.
- **Serving `dist` same-origin is the recommended path for local production**, not just for a future Railway deploy. `apps/server/AGENTS.md:13` already lists "serve `apps/web/dist` from the server" among the Railway checklist items; a grep across `apps/server/src` for `static`/`dist` finds nothing yet, so it isn't built. `apps/web/AGENTS.md` now has a "Local production" note pointing at this same gap for the teacher's own machine — the two should land together, not only as part of a remote deploy.
- **E2E contract notes.** `apps/web/src/lib/api.ts`'s reducer (`applyEvent`, line 291; `withMessage`, line 341; file ends line 368) treats every server event defensively: an unknown `type` (checked against `EVENT_TYPES`, line 101), a missing `payload`, or an id that doesn't resolve (`authorId`, `channelId`, a cited `cardId`, `card.published`'s `authorId`) is logged with `console.warn` and dropped or degraded rather than applied — because `CommunityProvider`'s lookups (`community.tsx:131` — `must()`) throw on a dangling reference. Any new event Codex adds needs to match an existing shape in `EVENT_TYPES`/`applyEvent` or the client will silently ignore it; worth a line in the API change doc so it isn't a silent gap in the demo.
- **`useConnectedCommunity` (`community.tsx:245-296`) does the initial `GET /api/community` before opening the WS** — the code now says so explicitly in a comment at line 255 ("Bootstrap: GET first, WS only after. Events that land in between are lost; for this weekend's local scope that's good enough"). Closed on 2026-08-23: the client now resyncs (`GET /api/community` → `resync` action) on every WS open, on `visibilitychange` → visible and on `online`, so the GET→WS gap and any disconnect are covered.
- **`lib/api.ts`'s events are still a hand-mirror of the contract.** `packages/protocol/src/events.ts` exists and task 1.4b is done, but `api.ts` still declares its own `ServerEvent`/`CommunitySnapshot` (the header comment now says so explicitly). The shapes agree today; switching to `import type … from "@ada/protocol"` is the one-line step that stops them drifting.

### Found by the E2E run against the real server (2026-08-22, rounds 1–3)

Observed with `apps/server` on :8787 (seeded), a fake runner on `/ws/runner?token=ada-demo-token`, and the SPA through the Vite proxy. Each item names what the client does about it today and what the server should decide.

- **The server doesn't validate card references in runner messages.** `message.create` with `fromCard: { cardId: "no-such-card" }` (and the same for `cite` blocks and `publishes`) is ACKed `ok:true` and persisted. Before the fix this blanked the whole SPA on every reload (the provider's lookups throw). The client now degrades (`sanitizeSnapshot`/`degradeMessage` in `apps/web/src/lib/api.ts`: the seal is dropped, the citation becomes text, with a `console.warn`), but a runner author gets silent data loss. Recommendation: reject unknown card ids the way an unknown `threadId` is already rejected, and name the offending field in the ack error.
- **Runtime/model reported over `presence` is not persisted.** After a runner reconnect without a new `presence` frame, `member.presence` carries no `runtime`/`model`, so the agent card drops the "· claude" chip and falls back to the seeded `provider.model`. Decide: persist the last reported runtime/model on the agent member, or require the runner to re-announce on every connect (and don't mark it `online` until it does).
- **Model shape is inconsistent between sources.** The seed's `provider.model` is a display name ("Claude"); the runner reports an API id ("claude-sonnet-4-5"). The same UI slot flips between them. Pick one shape or give the protocol `displayName` + `modelId`.
- **Mentions are dropped, not queued, while the runner is offline.** "@ada hi" posted with the runner socket down is stored and broadcast, but the runner never receives `agent.mention` after reconnecting. The composer copy was softened to "The message still goes into the channel" (no promise of delivery). If the demo relies on "start the runner later and it catches up", the server needs an undelivered-mention queue.
- **`thread.created` doesn't mark the root message.** `createThread` inserts the thread row only; `replyIds` are derived from `messages.thread_id`, so the root must never get `thread_id` server-side — but the client convention (`demo.ts`) is that the root carries `threadId`. The client now patches the root's `threadId` itself on hydration and on `thread.created`. Worth documenting the convention in the community-server spec.
- **`cite` block `text` is advisory.** The runner emitted `text` = the raw card id; the client ignores it and renders the card's title. State it in the protocol (or have the server fill `text` with the title) so a less forgiving client doesn't render a uuid pill.
- **Through the Vite proxy a dead server is a 502, not a network error**, so `api.ts`'s "Is it running? Try `npm run dev:server`" hint never fires; the user sees "The server responded 502". The client now treats 502/503/504 on `/api/community` as "server not reachable" and shows the hint (`fetchCommunity`, `api.ts`).
- **`npm run seed` is additive, not a reset.** Re-running it keeps earlier messages and cards; a fresh DB needs `rm -f apps/server/data/ada.db*` first. Add a `--reset` flag or document it in `apps/server/AGENTS.md` so demo rehearsals start clean.
- **The server forwards an agent's own message back to it as a mention.** Ada's answer said "mention me with @ada ingest" and the server emitted `agent.mention` for it; the runner now ignores mentions whose `message.authorId` is the agent itself, but the server should skip self-mentions (and, ideally, mentions inside agent messages altogether) so every runner doesn't have to.
- **`card.publish` validation errors are opaque** (`"invalid runner message"` for an invalid `type`). Echo the failing field and the allowed values (`note|assignment|decision|answer|submission`).

## Method

- **5 code auditors**, one per dimension (a11y, performance, responsive, theming, implementation integrity) **+ 1 browser auditor**, produced the pre-fix Health Score and the confirmed/documented finding split above.
- **Adversarial verification** was run on the P0/P1 findings before assigning fixes; the P2/P3 set was recorded but not independently re-verified before the fix round.
- **Two reconciler agents** applied fixes by exclusive file ownership (6 files each, no overlap): one on `screens/Channel.tsx`, `lib/community.tsx`, `components/ada/folder.tsx`, `components/ada/channel.tsx`, `components/app-sidebar.tsx`, `App.tsx`; the other on `components/ada/identity.tsx`, `components/ada/panel.tsx`, `components/ada/markdown.tsx`, `components/ada/message.tsx`, `components/ada/card.tsx`, `index.css`.
- An **integration gate** ran after both reconcilers finished, over the union of 12 modified files: checked for broken imports, renamed props, unused variables, and non-English text. Zero errors on the first pass.
- **E2E** was exercised against the real `apps/server` with a fake runner standing in for an AI provider — not mocked at the client — per the reconcilers' in-browser verification notes (localhost:5173: live presence labels reading "Martin · online", x-ray lines redrawing on scroll/resize with no polling, a disabled button's `aria-describedby` resolving to its reason, the card panel's H2→H3 outline).
- **This report's re-verification** (this session, after group 5's connected-mode work landed on top of the fixes): every file:line citation above was re-checked with `grep -n` and direct reads against the current working tree, not assumed from the first draft; file mtimes (`stat -f "%Sm %N"`) were used to identify which files had changed since the fixes were first verified (10 of 15 touched files changed again between 21:13 and 22:35); a fresh `npm run typecheck && npm run lint && npm run build` was run and the warning count corrected (18, not 17).
